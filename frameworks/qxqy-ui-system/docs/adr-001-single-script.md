# ADR-001 · 教程 UI 用「一份脚本」还是「独立脚本映射」

- 状态：**已采纳**（单脚本）
- 日期：2026-10-20
- 决策：**不新建脚本映射放教程；教程作为主脚本里的一个模块（bundle）运行。**

## 1. 问题

教程 UI 系统（本框架）要不要像"关卡主体"那样单独建一个脚本映射？
关心点是：**教程与关卡主体的交互会不会因为拆开而更麻烦**。

## 2. 事实（决定依据）

| # | 事实 | 来源 |
|---|---|---|
| 1 | 脚本都挂在**具体客户端控件**的「脚本」页签上；只有**建立了映射**的 `.lua` 才会被打包上传 | 《客户端控件和客户端脚本》§七.3；`docs/api-notes.md` §11 |
| 2 | 跨脚本只有两条路：`ctrl:GetScript(scriptMappingId)` → `script:Invoke(全局函数名, …)`，或服务端信号 | 《客户端控件API文档》§5(2)/§13(4)；`docs/api-notes.md` §4 |
| 3 | `script:Invoke` 调的是**目标脚本内的全局函数** ⇒ 两个脚本各有自己的全局环境，**不能共享 Lua 表** | 同上 |
| 4 | 联机信号延迟**最低 100ms** ⇒ 用信号做教程↔关卡联动必然异步 | 《客户端控件和客户端脚本》§五.1 |
| 5 | 按键监听回调"返回 true = 已处理"只保证**同一容器内**其它控件不再响应；跨容器/跨脚本的先后由渲染顺序决定 | 《客户端控件API文档》§13(5)；《客户端控件和客户端脚本》§五.4 |
| 6 | 传送/断线重连会**销毁全部客户端控件**并回到初始状态，界面恢复要自己写 | 《客户端控件和客户端脚本》§五.3 |
| 7 | `scriptMappingId` 在真机导入后可能重映射，需要按语义校准（本工作流专门有一节索引校准） | 模拟器能力文档 §5 导入后校准 |
| 8 | 两份映射 = 两份 bundle = 两份控件索引（DFS）、两套输入监听、两套恢复逻辑、两次交付校验 | 工程常识 + 事实 5/6 |
| 9 | `[实测]` 本宿主**再次导入同一存档会多出一条脚本实例**（id 冲突时分配新 id），多实例问题已经踩过一次 | `records/playtest.md` §交付物自检 |

## 3. 结论与理由

**单脚本**。拆开不是"更麻烦一点"，而是把三个本来可以在一处裁决的问题拆到两处：

1. **状态共享**：教程要读关卡状态（第几关、进度、是否已看完教程、是否允许翻页）。
   同一脚本里就是一个 Lua 表；拆开只能 `Invoke`（依赖会变的映射 id）或信号（≥100ms + 服务端绕一圈）。
   ⇒ 教程与关卡的"实时联动"在拆开后不可能做到同步。
2. **输入裁决**：教程开着时按 Esc 应该是"关教程"还是"取消关卡里的选择"？
   单脚本里是**一个分派器里的一个 if**；两脚本里是两套监听抢同一次按键，谁赢看渲染顺序，
   而且没有任何一处代码能看到全貌。
3. **成本翻倍项**：控件索引、生命周期恢复（传送/断线）、bundle 维护、映射与索引校准、交付自检。
   收益只是"文件更小/可以分开改"——这个收益用一个模块开关就能拿到（见 §4）。

## 4. 怎么落地（已实现）

同一份 `lua/src/`，两种打包形态：

| 形态 | 产物 | 谁定义生命周期 | 用途 |
|---|---|---|---|
| `--mode standalone` | `lua/main.lua` | bundle 自己注册 7 个全局回调 | 教程单独跑 / 演示 / 排障（当前交付形态） |
| `--mode module` | `lua/module.lua` | **不注册任何全局回调**，只暴露全局 `Tutorial` | 并入关卡主脚本 |

并入主脚本的写法（`lua/module.lua` 粘到主脚本顶部，或 require）：

```lua
local T = Tutorial.install({
  root_name   = "tutorial.root",   -- 教程自己的整屏根容器（和关卡 UI 分开）
  keys_enabled = false,            -- 关键：按键由主脚本裁决
  log_prefix  = "[tutorial]",
})

function OnStart()  T.OnStart() end          -- 主脚本已有自己的 OnInit/OnStart
function OnUpdate(dt)
  T.OnUpdate(dt)                             -- 只转发 dt（长按计时用）
  -- …关卡自己的逐帧逻辑
end

-- 教程 ↔ 关卡：同一 Lua 环境，直接调用/读表即可
if level.tutorial_shown then T.act("close") end
local st = T.state()                         -- {screen=, page=}
```

### 为什么这样不会和关卡 UI 打架

- `App` 只从**自己的根容器**（`tutorial.root`）往下建索引（`Bind.rebuild({root})`），
  控件名只需在这棵子树里唯一 ⇒ 不会和关卡的 `hud.*` 撞。
- `keys_enabled=false` 时框架不绑键盘，也不抢任何全局回调。
- 想临时"关掉教程"：`Tutorial.install{ auto_open = false }`，或运行时 `T.hide()`；
  **不需要摘掉一份脚本映射**。

## 5. 什么时候才该拆成独立映射（判定条件，满足任一条再说）

1. 教程要**运行时实例化多份**（例如每关一个模板实例、各自独立状态）——
   因为模板脚本随实例存在，此时"一份脚本多实例"反而是官方支持的形态；
2. 教程要**独立发布/复用到别的关卡**（不同 GIA 资产、不同作者维护）；
3. 教程必须**在没有关卡脚本时也能跑**（纯教程关/独立演示包）。

三条都来自"生命周期边界"，而不是"代码组织"——代码组织用模块就能解决，不需要付跨脚本的代价。
