# 2 用例

**什么时候是这一步**：规则清楚了，要定"什么算通过"。

**做完的标志**：P0 与高风险边界都有用例，每条有明确 oracle，静态校验通过。此时只能说**用例已制定**，不能说"已通过"。

本步骤**只做静态检查**：不启动模拟器、不改存档、不跑 `runCase`。

---

## 怎么想

### 写用例前先问：这条断言能不能证明我想证明的事（P3、P7）

对每条断言问两句：

1. **反向也成立吗？** 如果被测代码被删掉，这条断言还会不会通过？
   - 「隐藏后控件不可见」——对一个从未被创建的控件也成立，**删掉代码照样绿**。
   - 改成「隐藏后不可见，**且**同层其它控件仍可见」，才真正测到了隐藏。
2. **它的 oracle 是什么？** 玩家看得见的东西 > 稳定的领域事件 > 诊断字段。**不要断言在内部实现上**——否则实现错了，测试会跟着一起错。

### 不要复制生产算法

测试里重算一遍生产逻辑，等于把同一个错误写两遍。断言**可观察结果**，不要重算过程。

### 一个用例只证明一件事

同时改多个变量或覆盖多个状态转换，失败后**无法归因**（P10）。拆开。

### 确定性

运动、冷却、计时显式消费 `dt`；随机玩法由配置/变量/首事件注入可复现的 seed 或序列。用例不依赖墙钟、机器速度或偶然帧。

---

## 要产出什么

`workspace/<slug>/tests/*.json`，每个用例一个文件。

**格式与每个断言 kind 的必填字段见 [平台事实 §2.5](platform-facts.md#25-用例格式208-实测-schema)——不要自创 schema。** 缺字段的用例要到运行期才失败，等于浪费一轮。

执行方式有个坑：用例存成文件是给人读与版本管理的，但 `runCase` **只接受对象**——要用文件工具读出 JSON 再作为 `args.case` 传入。相关工具语义见 [平台事实 §2.4](platform-facts.md#24-工具与动作)。

### 覆盖什么

P0 基线四件：`boot`、`first-success`、`first-fail`、`restart`，加一个 `mobile-smoke`（最短成功路径 + 整屏可见 + 不崩溃 + 关键状态）。

再按玩法扩展边界：碰撞边界、连点/连触、暂停恢复、二次重开、掉帧大步长、触控热区、服务端变量/信号路径、其余画布 smoke。

**按风险排序，不追求覆盖率百分比**：高风险、高频、最近出过缺陷、状态转换复杂的优先。

### 追踪表

只需要能让"规则 → 用例"对得上。一张两列表就够（规则/不变量 → 用例文件 → oracle）；条目多了再考虑加列。

---

## 反模式（出现即返工）

- 用 `assert log contains "fun"` 之类断言代替体验判断——体验由人看，不由日志宣布。
- 断言写在诊断字段上，而玩家可见控件明明可以断言。
- 用例依赖墙钟、机器速度或偶然帧。
- 为让用例变绿而修改期望值或删除失败用例（见 [P8](reasoning-patterns.md#p8--删掉的东西要变成哨兵)）。
- 一个用例同时改多个变量或覆盖多个状态转换。
- 在本步骤就跑 `runCase`。

---

## 静态校验（本步骤唯一允许的执行动作）

确认：JSON 可解析、`format`/`version` 正确、每条断言字段齐全、引用的控件名与策划案一致、事件 kind 合法、`dt` 为正数。

**只写"用例已制定"，不要写"已通过"。**

---

## 关于 Red

**有效 Red** 要等步骤 5 有可运行骨架后，由**目标生产行为缺失**产生。

下面这些**不算** Red：坏 JSON、路径错误、事件到不了控件、模拟器没启动、工具故障。
已有完整行为的工程**不要为制造 Red 而删除生产代码**。
