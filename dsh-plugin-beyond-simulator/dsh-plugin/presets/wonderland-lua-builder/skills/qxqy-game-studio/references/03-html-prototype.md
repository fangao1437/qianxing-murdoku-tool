# 3. HTML 效果展示

## 输入与适用时机

读策划案与步骤 2 已制定的用例名。网页只用于确认**画面、操作与节奏**，不验证平台行为；已有工程的窄修复可跳过并记录理由。本步骤不操作模拟器。

## 执行动作

产出可打开试玩的 `prototype/`，覆盖开局、第一次成功、失败与重开：

```text
prototype/index.html
prototype/README.md    启动方式、操作、不可移植项、坐标差异
```

### 与策划案对齐（否则反馈无法落到规则上）

- 状态与事件名与 GDD 契约一致（`boot/ready/playing/resolved/restart`、成功/失败原因），这样用户的一句反馈可以直接映射到哪条规则要改。
- 只实现 P0 与本次要确认的少量差异；不要顺手加商店、成就、多关卡。
- 用与步骤 2 相同的用例名标注可玩场景（`boot`/`first-success`/`first-fail`/`restart`），方便下一步对照。

### 请用户确认什么（一次问清，不要反复问）

给用户一个观察清单，而不是"你觉得怎么样"：

| 观察项 | 具体问题 |
|---|---|
| 易懂 | 不看说明能否完成第一次有效操作 |
| 反馈 | 成功/失败是否立刻可感知，能否说出失败原因 |
| 节奏 | 单局时长、等待、冷却是否合适 |
| 触控 | 热区是否够大、单手能否操作 |
| 画面 | 层级、可读性、配色是否可接受 |

### 记录与分类

- 试玩记录标 `runtime=html`；没有浏览器操作工具时标 `browser-run: user`，**不能声称 Agent 已亲自试玩**。
- 把网页画面与动画分为 `must-reproduce`、`can-degrade`、`concept-only`，写清哪些效果必须在千星重新实现、哪些可以降级或舍弃。
- 网页新增或变更规则时回写策划案与用例。
- 时间盒：演示够确认体验即可；把它做成成品不如把时间花在步骤 5–6。

### 边界

- HTML 不是 Lua 源码、不是交付物；**不逐行翻译 DOM/CSS/JavaScript**。
- HTML 通常原点左上、Y 向下；千星原点左下、Y 向上。不可直接复制坐标或 CSS 像素。
- 网页可玩只证明 HTML 演示的结果，不能当作模拟器或真机证据。

## 产物与完成条件

产物为可打开的 HTML 演示、`prototype/README.md`、`records/playtest.md` 中的体验反馈与不可移植项清单。用户已确认核心画面、操作与节奏；需要改的规则已回写契约与用例。
