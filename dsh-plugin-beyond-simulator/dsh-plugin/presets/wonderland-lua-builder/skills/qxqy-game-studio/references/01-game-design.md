# 1. 策划案

## 输入与适用时机

新游戏的想法、参考图、目标设备与用户约束；已有工程只补齐影响本轮任务的规则。先完成 [PREFLIGHT](workflow.md)，并读 [平台事实](platform-facts.md)中与玩法相关的小节。本步骤不打开模拟器、不改存档。

## 执行动作

### 收敛为一局完整体验

写清：目标玩家与熟练度、典型场景、单局时长、**唯一核心动词**、最短循环、成功/失败/反馈/重开、PC 与手机输入、P0/P1/不做项、美术意图、关键风险。
核心循环必须能写成一句：`目标 → 操作 → 即时反馈 → 局势变化 → 成功/失败 → 重开`。写不成一句说明玩法还没收敛。

### 分析完整性清单（逐项给结论，不适用就写"不适用"）

| 项 | 要回答的问题 |
|---|---|
| 首 30 秒 | 开局看到什么、第一次有效操作是什么、多久获得第一次成功反馈 |
| 失败可读性 | 玩家能否说出"我为什么输了"；失败是否有可归因的即时反馈 |
| 难度与节奏 | 难度如何随时间上升；有无"必输"或"必胜"的退化状态 |
| 数值 | 关键数值（速度、冷却、计分、时长）的初值与调整范围；哪些是可比较参数 |
| 反馈通道 | 每次操作后的可见反馈是什么；去掉音效/动效后是否仍然成立 |
| 边界情形 | 暂停、连点/连触、重复开局、二次失败、切画布、中途退出、断线或重连 |
| 可访问性 | 颜色之外的区分手段、文字大小与语言、闪烁、单手/双手、触控热区 |
| 平台依赖 | 玩法依赖哪些平台能力（列表滚动、音频、动效、模板实例化、多指）；其中有缺口时的替代方案 |
| 规模 | 预计控件数量与层级、逐帧工作量；是否触到规模上限（见平台事实上限节） |
| 风险 | API/GIA/资产/真机四类风险各自的最晚验证阶段 |

**平台依赖要先做可用性预检**：把玩法需要的平台能力对照 [platform-facts.md](platform-facts.md)§1–§2。已知在模拟器缺失（音频、图片素材预览、网格列表项滚动、动效播放、模板引用链）的能力，不要作为 P0 的唯一反馈或唯一验证途径；要么给替代实现，要么明确写入真机核验项。这一步提前做，能省掉后面整轮返工。

### 分类每条陈述

- `HYPOTHESIS`：可由试玩判断的体验假设（附任务与观察点，不泄题）。
- `CONTRACT`：可测试的规则（状态、胜负、计分、冷却、碰撞边界、输入语义、服务端变量/信号）。
- `UNKNOWN`：需要官方文档、探针或真机证据的平台事实（写明验证方式、负责人、最晚阶段）。

真正存在玩法分歧时给用户 2–3 个可比较选项与推荐；函数名、控件拆分、目录结构自行决定。

### 玩法规格（P0 契约的展开）

放进 GDD，或复杂时另建短的 `docs/game-spec.md`：

- 状态机：`boot → ready → playing → resolved(win|fail) → restart`；P0 需要暂停就一并建模。
- 状态数据、生命周期、客户端/服务端权威划分（客户端读变量 + 发信号，服务端写变量）。
- 输入动作、前置状态、节流、热区、无效输入与结束后行为。
- 显式 `dt`、位置/速度/碰撞边界、可注入 seed 或固定序列。
- 成功/失败/重开、领域事件、稳定日志与错误降级。
- 每条不变量（INV）及其可观察 oracle。
- 未知平台事实、责任人、探针或真机验证。

规格描述状态与玩家动作，不提前绑定 DOM 选择器、CSS 类或 JS/Lua 函数名。只有 HTML 与 Lua 确需共用结构化规格时才加 `prototype/game-spec.json`。

## 产物与完成条件

产物为 `docs/gdd.md`，按需附 `docs/game-spec.md`。一局体验、P0 范围、输入与胜负语义已明确；分析清单逐项有结论；平台依赖有替代方案或真机核验项；未知项有验证方式与最晚阶段。只锁定需要用户判断的产品决定。
