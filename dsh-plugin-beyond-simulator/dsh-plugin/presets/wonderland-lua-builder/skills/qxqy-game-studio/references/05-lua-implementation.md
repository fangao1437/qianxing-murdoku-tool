# 5. Lua 编码实现

## 输入与适用时机

读策划案、`tests/*.json`、美术清单与 UI 还原方案；已有工程同时读存档、源码与最近结果。**从本步骤开始操作模拟器。**

写依赖编辑器 API 的 Lua 之前，复用 [PREFLIGHT 已核验的知识来源](workflow.md#知识库发现与可用性核验)定向核对所需官方 2D/Lua 文档，并回读 [平台事实](platform-facts.md)中相关小节。新增 API 资料缺失时先查已配置来源，仅请用户补齐仍缺的内容；不从普通 Lua/UI 框架或 3D 节点图经验猜接口。未知语义先查文档或做单问题探针，探针不进生产路径。

## 接入模拟器与搭建骨架

用当前宿主的工具说明与实际 schema；有 `qxqy-simulator` 操作 Skill 时按需加载（MCP 不自动附带该 Skill）。MCP 宿主还需 `handle`：先 `qxqy_project_open`，工程操作都带该句柄——不要照搬 Harness 示例而漏参数；Harness 无 `qxqy_project_open`。

### 工程与存档纪律

- 三类资产：服务端 UI 容器、客户端 UI 模板、Lua 脚本。脚本只挂客户端控件/模板；服务端"客户端控件容器"不能挂脚本。
- 数据写操作**尽量**带最新 `expectedRevision`（省略时按内存当前状态直接生效，可能覆盖别的改动）；成功后 revision +1；冲突时重新 `get` 再算，不要盲目重试。
- 内存修改与试玩不会自动落盘，而 **Harness 工具集里没有保存操作**：落盘要请用户在"模拟器"标签点【保存存档】。目标路径 `workspace/<slug>/<slug>.save.json`（文件头附近含 `"format": "qxqy-simulator-save"`）。需要实机脚本复制时，必须先让用户保存，且保存后不再改动存档，否则复制会被拒。
- `scripts[].source` 非空 ⇒ 试玩运行内联源码；只改外部 `.lua` 不同步内联源码 = 仍跑旧代码。每次改脚本后**同时**同步两处。
- 控件优先"少量基础模板 + Lua 实例化/改属性"：用 `game.InstantiateClientUIControl(prefabIndex, parent)` 创建，再由 Lua 设布局、文本、图片与可见性。官方限制：**只有存为模板的客户端控件的父节点能被动态创建**，主屏控件与模板子节点都不行。
- 目前对 GIA 的认识不完整：在 UI 侧（存档/模板）直接定义复杂控件树或属性，导出或真机导入可能不兼容；确需在 UI 侧定义的字段记入真机核验项。
- 按需导出 GIA；**GIA 不保存脚本挂载关系**，挂载点要单独记录。

### 实现规则

| 主题 | 规则 |
|---|---|
| 时间 | 计时显式消费 `dt`；随机玩法用可注入 seed/序列；规则与 UI 副作用分离 |
| 调用约定 | `game` 是全局表：用点号 `game.X(...)`，注意参数个数；误用冒号在模拟器可能静默通过、真机报错 |
| 图片 | 改图用 `SetImage(imageSource, imageId)`；`imageId` 只读；`imageSource` 与 ID 成对匹配 |
| 文本 | 属性写不进去时（`.text` 可能为 nil）退回 `SetText`；保留必要 `pcall` 层级，不要为"统一写法"删掉容错层 |
| 输入 | **没有长按事件**：用 CursorDown/CursorUp + 显式 `dt` 累计实现长按，并定义阈值与取消条件；容器 `showCursor` 必须为真光标事件才有效 |
| 事件 | 按键回调返回 boolean 表示"已处理"，否则同容器其它控件会重复响应；按键按渲染顺序派发 |
| 服务端 | Lua 只读变量 + `SendSignal()`；**不能写自定义变量**；变量变更回调不给值，需自行 Get；联机信号最低 100ms |
| require | 用导入根前缀：映射 `workspace/<slug>/draws.lua` → `pcall(require, "default_import_file/workspace/<slug>/draws")` |
| 规模 | 注意逐帧工作与控件数量；循环内高频调用会导致进关卡死且日志不报错 |

### 布局与素材

- 原点左下、锚点相对父矩形 0–1；以 `mobile-16-9`（1280×720）整屏完整可见为基准，PC 用固定设计板 `min(canvas/design)` 等比放大、不足留边。
- 缩放容器上不要再加全屏不透明兄弟节点（同级先出现的子节点会盖住舞台）。
- 接入步骤 4 的素材；缺失框记录真实 `targetId`。文本框建议开启 `adaptiveFontSize = true` 并设最小字号，`fontSize`/`minimumFontSize` 必须是整数；自适应字号与换行在模拟器上不完整，真机确认文字是否完整可读。
- 旋转会进入运行时，但点击命中按旋转前轴对齐矩形计算——需要"看得见也点得到"时，别用旋转做命中区域。

### 性能与度量

先测量再优化，且测量的树必须与存档真实结构一致：用与真实结构不符的替代树做探针，会把开销记到错误的版本上（曾有"每次渲染 972→132 次引擎调用"的结论因探针树缺控件被推翻）。汇报性能时写明工具、粒度与样本；没有真机数据就不要给毫秒结论。

## Red→Green→Regress

1. **建可加载的最小骨架**：先排除 JSON、路径、挂载、事件路由与工具故障——坏 JSON、路径错误、事件到不了控件、模拟器未启动都不算 Red。
2. **跑步骤 2 的用例**，确认目标生产行为缺失导致**有效 Red**；新游戏的 `first-success`、`first-fail`、`restart` 至少各有一次有效 Red。保留 `failedAt`、帧号与现场快照。
3. **一次实现一条规则**，执行目标 Green 与相关 Regress；已有规则缺陷先补最小失败用例。纯文案等窄改动按风险检查，不人为破坏已有行为制造 Red。
4. **断言双向**：改了什么就同时断言"该变的变了""不该变的没变"。
5. **确认测试真的跑到了新代码**：有打包/拷贝环节时先重新打包再测，否则绿灯没有意义。
6. **写入生效检查**：请用户保存落盘后，从磁盘重新读取并做字段 diff（往返字节相等不能证明生效；也不要拿"工具返回成功"当证据）。
7. 记录：

```text
case / red reason / failedAt / frame
minimal change / target result / full regression
screenshot or snapshot / remaining risk / 证据标签
```

只按策划契约实现玩法，**不逐行翻译 HTML DOM/CSS/JavaScript**。
