# 接入、跨步骤决策与恢复

首次进入或恢复会话时读本文件，再读 [平台事实与已知边界](platform-facts.md)，然后按 [步骤索引](../SKILL.md#按需读取)只读当前一步。七个步骤各自维护操作细节；本文件只负责接入、门禁、证据与回退。

## PREFLIGHT — 接入与基线

1. **盘点输入。** 用户想法、参考图、已有 Lua/GIA/存档、反馈与约束；读工作区 `AGENTS.md`、README、项目索引。
2. **找知识来源。** 按下方[知识库发现与可用性核验](#知识库发现与可用性核验)检查工作区与当前 AI 宿主已配置的资料来源；不要一开始就要求安装插件或补文档。
3. **核对能力。** 检查会话实际提供的模拟器、浏览器与美术能力；目录存在或安装成功不等于工具可见。记录插件版本（模拟器能力与版本强相关）。
4. **读已有产物。** 已有工程先读 `docs/production-plan.md`、`docs/gdd.md`、`tests/`、`records/playtest.md`、存档与源码，找出本轮目标与**最早缺失的证据**，确定唯一当前步骤。
5. **写计划。** 在 `docs/production-plan.md` 记：当前步骤、目标、进入证据、退出证据、阻塞项、下一步。只创建当前任务需要的文件，不为空阶段建占位产物。
6. **登记平台事实。** 把本轮要依赖的平台能力与 [platform-facts.md](platform-facts.md) 对照；不确定的标 `[推断]` 并安排最小验证。

PREFLIGHT 不计入七步。新游戏按 1→7；已有工程与窄修复按证据选择步骤。

## 知识库发现与可用性核验

启动制作前完成一次有范围的检查；恢复会话时复用已记录来源，工具/资料版本或涉及 API 变化时定向复核。

1. **先查工作区入口。** 从 `AGENTS.md`、README、项目索引及其引用位置找官方 Lua API、客户端脚本使用指南、控件/模板与脚本挂载说明、已知问题与真机记录。检查项目内的 Skill、MCP 或插件配置；本地知识库可能在 Git 忽略目录里，按已发现的目录定向检索，不扫描整块磁盘。
2. **再查当前 AI 宿主的配置与能力目录。** 用宿主提供的插件、MCP、Skill 列表；必要时只读已知项目级/用户级配置中相关的名称、启用状态、资源入口与本地路径，寻找 `miliastra-toolbox` 系列、其它知识库服务及本地文件知识库。名称可能是别名，不能只凭插件名认定覆盖范围；不改配置、不回显令牌或无关内容。
   在本工作流的 Harness 环境里，2D 客户端资料通常由知识库插件的 `miliastra-knowledge-lua` Skill 提供（配 `list_client_documents` / `get_client_document` 两个工具，语料在远端）；而 `miliastra-knowledge` 与 `rag_search` 只覆盖**服务端/3D 节点图**，不能用来回答客户端 2D 问题。没有"名字叫 miliastra-toolbox 的工具"——要按插件与 Skill 名去找。
3. **核验实际内容。** 对候选来源检查本会话能否调用/读取，再定向取一段官方 Lua API 与使用指南，确认属于千星客户端 2D UI + Lua，并能读到函数签名、参数/枚举与操作说明。不要为检查可用性加载整套文档。只提供 3D 节点图资料、只有检索摘要、或接口表缺失的来源，不算取得所需 Lua 官方资料。
4. **记录来源与缺项。** 在 `docs/production-plan.md` 记：来源名称、工具/路径、文档标题、版本或日期、适用范围、读取结果。区分三种状态：**已配置** / **本会话可调用或可读** / **已取得本轮所需官方资料**；配置不可读或工具未加载时记"尚未核实/当前不可用"，不推断用户没有配置。官方文档、实战经验、真机观察、模拟器策略分别标注；版本冲突先核对来源，不拼凑签名。
5. **优先复用，再补缺项。** 已有资料够用就继续，不重复要求安装；连接不可用但本地资料够用时用本地资料并记录来源。只有缺本轮所需内容时，简短说明缺哪份资料或哪个能力，请用户启用连接、给可读路径或补文档。步骤 1–4 可继续；依赖缺失 API 的 Lua 实现必须等资料补齐。

向用户简述找到的可用来源与实际缺项即可，无需报告全部配置清单。模拟器可用与知识库可用分别检查，不能互相替代。

## 证据登记表（每轮维护）

每条结论一行，缺任一项就不算证据：

| 结论 | 标签 | 来源（文件/工具调用/帧号/截图） | 复核方式 | 有效期 |
|---|---|---|---|---|
| 例：金币变量在结算后 +1 | `[实测]` | `runCase first-success` 输出、帧 412 | 重跑该用例 | 本轮存档 |

约定：模拟器结果不写成真机结论；上游文档结论标 `[官方]` 并注明文档标题；未能验证的标 `[未验证]` 并写"谁来验、何时验"。

## 步骤门（进入/退出）

| 步骤 | 进入条件 | 退出条件（缺一不算完成） |
|---|---|---|
| 1 策划案 | 有想法/参考/待补规则 | GDD 写清核心循环、输入、胜负、P0 与不做项；未知项有验证方式与最晚阶段 |
| 2 TDD 用例 | 规则明确 | 追踪表 + `tests/*.json`；静态校验通过；列出用例清单与优先级（此时写"用例已制定"） |
| 3 HTML 展示 | 契约与用例名已定 | 可打开试玩的演示 + 不可移植项 + 用户反馈记录（`runtime=html`） |
| 4 美术 | HTML 体验已确认 | 参考图、素材清单、目标 ID/图元、UI 还原方案；缺失项标真机核验 |
| 5 Lua 实现 | 前三步产物齐 | 可加载 Lua + 完整存档 + 挂载/架构说明；目标用例经历有效 Red→Green→Regress |
| 6 测试 | 有可运行版本 | P0 与边界回归结果、截图、日志、缺陷闭环、已知限制；状态=模拟器候选 |
| 7 真机验证 | 模拟器候选 + 交付清单 | 导入/挂载与索引记录、脚本更新方式与结果、真机证据或明确的未验证项 |

## 产物位置与恢复

`workspace/<slug>/` 是项目产物位置，下列路径相对该目录：

| 产物 | 用途 |
|---|---|
| `docs/gdd.md`、按需 `docs/game-spec.md` | 玩法语义、范围与契约 |
| `docs/production-plan.md` | 当前步骤、进入/退出证据、知识来源与版本、阻塞项、下一步 |
| `tests/` | 规则用例（`qxqy-autotest` 单用例文件）；测试 JSON 不是存档 |
| `prototype/` | HTML 展示与操作说明 |
| `docs/art-bible.md` | 参考图、目标素材、UI 还原规格与真机核验项 |
| `main.lua`、`<slug>.save.json` | 源码与完整工程；存档头部附近有 `"format": "qxqy-simulator-save"` |
| `docs/tech-architecture.md` | 文件/控件职责、变量/信号、数据流与脚本挂载 |
| `docs/device-handoff.md` | 真机导入、真实索引、脚本路径/挂载、同步方式与待办 |
| `records/playtest.md`、`export/` | 试玩/修复证据与交付资产 |

恢复会话时：先读实际产物与证据（`production-plan` → 最近 `playtest` → 存档/源码），再读聊天摘要；用户已给的信息直接复用，不重复索取。

## 回退与完成

- 设计问题：回步骤 1–3，更新契约与用例。
- 素材问题：回步骤 4，记录目标 ID 与还原方案。
- 规则或代码缺陷：补步骤 2 的最小用例，再到步骤 5–6 修复与回归。
- 真机差异：在步骤 7 留证，回受影响步骤修复，再验证真机结果。
- 平台能力缺口：不改玩法硬凑，按 [platform-facts.md §5](platform-facts.md#5-模拟器-vs-真机差异实测换版本要复核)判定"环境差异 / 真实缺陷"，把环境差异写进真机清单。

只加载受影响步骤，不把回退理解为整套重跑。真机未验证时交付状态为"模拟器候选"；只有目标行为有真机证据时才标记该行为通过。
