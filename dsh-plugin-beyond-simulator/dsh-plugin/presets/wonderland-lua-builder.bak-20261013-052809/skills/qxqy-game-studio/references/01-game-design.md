# 1 策划案

**什么时候是这一步**：想法还没收敛成能被测试的规则。

**做完的标志**：一局完整体验的契约已定；每个会影响实现的未知项都有验证方式与最晚阶段。

本步骤**不打开模拟器、不改存档**。

---

## 怎么想

### 先分叉，再收敛（P4）

在动笔写文档之前，先问自己：**达成这个体验有几种机制不同的做法？**

- 同机制不同参数不算分叉（「冷却 3 秒」和「冷却 5 秒」是同一个方案）。
- 不同机制才算（「冷却限制」/「资源消耗」/「动作队列串行化」）。

每个方案问四句：核心机制是什么 / 它让什么变简单 / 它让什么变难 / 什么情况下它是错的。

**什么时候可以跳过**：只有一种机制可行、或这是个窄修复时，直接做，不要为了流程而分叉。

### 玩法要能收敛成一句话

"玩家在 ______，通过 ______，获得 ______ 的感觉。"

**但不要套固定句式。** 涌现式、节奏式、沙盒式玩法可能写不成"目标→操作→反馈→局势→胜负→重开"。写不成那个句式**不等于**玩法没收敛——换成你自己的描述方式，只要你能说清玩家重复做什么、为什么想再做一次。

### 先把未知项钉在时间轴上

对每个 `UNKNOWN`：**它最晚必须在哪一步之前解决？** 没有这一列，未知项会一路漂到交付才发现。

需要查证的典型项：某个 API 到底存不存在、某个字段能不能写、某个能力模拟器支不支持。查法见 [平台事实的复核方式](platform-facts.md#0-复核方式) 与 [P6](reasoning-patterns.md#p6--结论即假设)。

## 要产出什么

一份 `docs/gdd.md`。**从模板复制**：[templates/gdd.md](../templates/gdd.md)。

模板里的小节**按需要保留，不适用的整节删掉**。不要为了"填齐"而写空表格——空表格比没有更糟，它看起来像已完成的工作。

必须落到纸上的只有三样：

1. **契约**——可测试的规则：状态、胜负、计分、冷却、边界、输入语义、客户端/服务端权威划分。每条不变量配一个可观察的 oracle。
2. **体验假设**——每条写清"什么样算被推翻"。写不出反例的，不是假设，是愿望。
3. **范围**——P0 是什么，什么明确不做。

以下**按需**回答，不强制逐项：
- 首 30 秒玩家看到什么、第一次有效操作是什么
- 失败是否可归因（玩家能不能说出"我为什么输了"）
- 难度如何随时间上升；有没有必胜/必输的退化状态
- 去掉了音效和动效之后，反馈还成不成立
- 边界情形：暂停、连点、重复开局、二次失败、切画布、中途退出
- 可访问性：颜色之外的区分、文字大小、单手操作
- 规模：预计控件数与层级、逐帧工作量

**这些问题是为了帮你发现设计漏洞，不是为了产出表格。** 有结论就写，没有就跳过。

## 平台依赖预检

把玩法需要的能力对照 [平台事实](platform-facts.md)§1–§2 检查一遍。

已知在模拟器缺失的能力（音频、图片素材预览、网格列表项滚动、动效播放、模板引用链）**不要作为 P0 的唯一反馈或唯一验证途径**。要么给替代实现，要么明确写进真机核验项。

这一步提前做，能省掉后面整轮返工。

---

## 提问边界

**真正存在玩法分歧时**，给用户 2–3 个可比较的选项与你的推荐（这正是 P4 的产出）。

函数名、控件拆分、目录结构**自行决定**，不要问。
