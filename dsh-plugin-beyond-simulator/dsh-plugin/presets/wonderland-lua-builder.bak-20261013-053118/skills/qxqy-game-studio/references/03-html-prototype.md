# 3 HTML 效果展示

**什么时候是这一步**：要确认画面、操作手感与节奏。

**做完的标志**：用户能打开试玩并给过反馈；不可移植项已记录。

已有工程的窄修复**可以跳过**本步骤，记下理由即可。本步骤**不操作模拟器**。

---

## 为什么要有这一步

网页只用来确认**画面、操作与节奏**——它不验证平台行为。它的价值在于：**在花代价做 Lua 之前，用最便宜的方式发现"这个玩法不好玩"或"这个操作别扭"。**

时间盒：够确认体验就停。把它做成成品，不如把时间花在步骤 5–6。

---

## 怎么想

### 分叉在这里最便宜（P4）

画面结构与交互方式才是真正要选的东西。给用户 2–3 个**机制不同**的方向，而不是一个做好的方案问"行不行"。

**在同一布局、同一玩法状态下**给方向，否则用户比的是画面精细度，不是设计。

### 让反馈能直接落到规则上

状态与事件名跟策划案契约保持一致（`boot/ready/playing/resolved/restart`、成功/失败原因）。这样用户说一句"我点不动"或"我不知道该干嘛"，你能直接映射到**哪条规则要改**，而不用重新猜。

### 一次问清，不要反复问

给用户一个**具体**的观察清单，而不是"你觉得怎么样"：

| 观察项 | 具体问什么 |
|---|---|
| 易懂 | 不看说明能不能完成第一次有效操作 |
| 反馈 | 成功/失败是否立刻可感知；能不能说出失败原因 |
| 节奏 | 单局时长、等待、冷却是否合适 |
| 触控 | 热区够不够大；单手能不能操作 |
| 画面 | 层级、可读性、配色能不能接受 |

### 边界（错了要返工）

- HTML **不是** Lua 源码，**不是**交付物。**不要逐行翻译 DOM/CSS/JavaScript。**
- HTML 通常原点左上、Y 向下；千星原点左下、Y 向上。**不要复制坐标或 CSS 像素。**
- 网页可玩**只**证明 HTML 演示的结果，不能当模拟器或真机证据。

---

## 要产出什么

```text
prototype/index.html
prototype/README.md    启动方式、操作、不可移植项、坐标差异
```

覆盖开局、第一次成功、失败与重开。

**只实现 P0 与本次要确认的少量差异**——不要顺手加商店、成就、多关卡。那些是下一步之后的负担。

### 记录

- 试玩记录标 `runtime=html`。没有浏览器操作工具时标 `browser-run: user`——**不能声称 Agent 已亲自试玩**。
- 把网页效果分成三类，写清哪些必须在千星重新实现：
  - `must-reproduce`——不还原就失去玩法
  - `can-degrade`——可以降级实现
  - `concept-only`——只是表达意图，不打算还原
- 网页新增或变更规则时，**回写策划案与用例**。
