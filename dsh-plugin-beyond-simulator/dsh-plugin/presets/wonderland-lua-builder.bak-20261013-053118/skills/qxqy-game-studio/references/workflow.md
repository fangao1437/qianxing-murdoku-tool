# 接入、恢复与回退

首次进入或恢复会话时读本文件，再按需查 [平台事实](platform-facts.md)，然后只读当前步骤的文档。步骤文档管操作细节；本文件管**接入、恢复与回退**。

---

## PREFLIGHT — 接入

不计入七步。做完这五件事，然后确定**唯一**当前步骤。

1. **盘点。** 用户想法、参考图、已有的 Lua/GIA/存档/反馈；读工作区 `AGENTS.md` 与项目索引。
2. **找知识来源。** 按[知识库核验](#知识库核验)检查本会话实际可用的资料来源。**先查工作区，再查宿主配置**；不要一上来就要求装插件或补文档。
3. **核对能力。** 模拟器、浏览器、美术能力在本会话是否**真的可调用**——目录存在或安装成功都不等于工具可见。记下**插件版本**：模拟器能力与版本强相关。
4. **读已有产物。** 已有工程先读 `docs/production-plan.md` → 最近的 `records/playtest.md` → 存档与源码，找出**最早缺失的证据**，据此定当前步骤。
5. **写下这一步要证伪什么。** 在 `docs/production-plan.md` 记：当前步骤、目标、**会推翻当前判断的观察**（P1）、阻塞项、下一步。

已有工程与窄修复按证据选步骤，不必从 1 重跑。

---

## 知识库核验
制作用到的 API 事实必须有来源。启动时做一次**有范围**的检查；恢复会话时复用已记录的来源，只有当工具/资料版本或涉及的 API 变化时才定向复核。

1. **先查工作区入口。** 从 `AGENTS.md`、README、项目索引及其引用处找官方 Lua API、客户端脚本指南、控件/模板与脚本挂载说明、已知问题与真机记录。本地知识库可能在 Git 忽略目录里——按已发现的目录定向查，**不要扫整块磁盘**。
2. **再查宿主配置与能力目录。** 用宿主提供的插件、MCP、Skill 列表；必要时只读相关的名称、启用状态与本地路径。**名称可能是别名**，不能凭插件名断定覆盖范围。不改配置，不回显令牌。
3. **核验实际内容。** 确认本会话**能否调用/读取**，再定向取一段官方 Lua API 与使用指南，确认属于千星客户端 2D UI + Lua，且能读到函数签名、参数/枚举与操作说明。**不要为确认可用性而加载整套文档。**
4. **分清三种状态。** 「已配置」/「本会话可调用或可读」/「已取得本轮所需官方资料」是三件不同的事。配置不可读只说明**还没核实**，不能推断用户没配置。

在本工作流的 Harness 环境里，2D 客户端语料由 `miliastra-knowledge-lua` 技能与 `list_client_documents` / `get_client_document` 提供；`miliastra-knowledge` 与 `rag_search` 只覆盖 3D 服务端节点图。没有名叫 `miliastra-toolbox` 的工具——按插件与技能名去找。

**缺资料时**：说清缺哪一份或哪个能力，请用户启用连接、给可读路径或补文档。步骤 1–4 可以继续；**依赖缺失 API 的 Lua 实现必须等资料补齐**——不要从普通 Lua/UI 框架或 3D 节点图经验猜接口。

## 结论的时效

`[官方]` / `[模拟器]` / `[实测]` / `[推断]` / `[未验证]` 用在**你要靠它做决定**的结论上，不是每条记录都要贴。用法见 [推理姿态 P1、P6](reasoning-patterns.md)。

需要标的时候：
- **模拟器**结果不要写成真机结论。
- **官方文档**结论注明文档标题与版本。
- **未验证**的要写清"谁来验、什么时候验"。

同一个结论如果在两个版本下不同，**先核对来源版本**再合并，不要拼凑。

## 产物位置

`workspace/<slug>/` 是项目根，下列路径相对它：

| 产物 | 用途 |
|---|---|
| `docs/gdd.md`、按需 `docs/game-spec.md` | 玩法语义、范围与契约 |
| `docs/production-plan.md` | 当前步骤、要证伪什么、阻塞项、下一步 |
| `tests/` | 用例文件（`qxqy-autotest` 单用例）。**测试 JSON 不是存档** |
| `prototype/` | HTML 展示与操作说明 |
| `docs/art-bible.md` | 参考图、目标素材、UI 还原规格与真机核验项 |
| `main.lua`、`<slug>.save.json` | 源码与完整工程；存档头部附近含 `"format": "qxqy-simulator-save"` |
| `docs/tech-architecture.md` | 文件/控件职责、变量/信号、数据流与挂载 |
| `docs/device-handoff.md` | 真机导入、真实索引、脚本路径/挂载、同步方式与待办 |
| `records/playtest.md`、`export/` | 试玩证据与交付资产 |

**恢复会话的顺序**：先读实际产物与证据（`production-plan` → 最近 `playtest` → 存档/源码），**再读**聊天摘要。用户已经给过的信息直接复用，不要重复索取。

## 回退

| 问题 | 回到哪里 |
|---|---|
| 设计/体验问题 | 回步骤 1–3，更新契约与用例 |
| 素材问题 | 回步骤 4，记录目标 ID 与还原方案 |
| 规则或代码缺陷 | 先补步骤 2 的最小用例，再回 5–6 修复与回归 |
| 真机与模拟器不一致 | 在步骤 7 留证，按[平台事实 §5](platform-facts.md) 判"环境差异 / 真缺陷"，再回受影响步骤 |
| 平台能力缺口 | **不要改玩法硬凑**；已缺失的能力要么给替代实现，要么写进真机核验项 |

回退只加载受影响的步骤。**真机未验证时，交付状态是"模拟器候选"**；只有目标行为有真机证据，才能说该行为通过。
