# 节点图编写与验证成果总结

更新日期：2026-11-22

## 工具链范围

本仓负责千星奇域节点图的结构读取、行为规格转换、TypeScript 生成、`.gia` 编译，以及把生成结果注入 `.gil` 副本。`.gil` 和 `.gia` 的原生字节生成由上游 `genshin-ts` 负责，本仓不直接编写 protobuf 节点图。

## 已完成能力

- 原生读取 `.gia` 的节点、端口、连线、常量、图变量和信号引用。
- 将可识别节点图转换为行为规格，并对分支、循环、复合节点、枚举常量、列表或字典常量等无法保持语义等价的内容分类拒绝。
- 从行为规格生成可读的 `genshin-ts` TypeScript 源码。
- 调用锁定版本 `genshin-ts 0.2.3` 编译 `.gia`。
- 将 `.gia` 注入已存在的 `.gil` 副本，并保留输入存档。
- 通过 `roundtrip` 对生成文件做编码往返校验。
- 通过节点定义、端口签名和别名表，减少节点标题、事件节点和多出参节点在转换过程中的歧义。

## 存档节点图实践

本项目曾用节点图工具完成以下类型的实验和核验：

- `murdoku/save` 的五参数保存信号，参数顺序为关卡 ID、局面码、步数、用时和通关状态。
- `murdoku/restore` 的恢复信号，参数顺序为局面码、步数、用时和通关状态。
- 局内存档结构体与列表泛型的读取、拆分、写回和节点端口绑定核验。
- 直接从已导出 `.gil` 样本中提取节点类型、结构体引用、信号绑定和端口信息，再生成可导入副本。
- 参考仓库中的节点图写回实现，处理事件节点标题与实际节点定义不一致的情况。

这些实践证明文件层的图写回、导入和编辑器结构回读可以自动化。正式游戏运行时是否执行节点图，仍需编辑器校验和千星沙箱实测，不能仅凭 `.gil` 可解析或往返字节一致下结论。

## 验证入口

```text
node test/run-tests.mjs
```

当前仓库已有离线回归为 186 项通过、0 项失败。生成或升级节点目录后，应重新运行该测试，并检查 `data/nodes.json` 的差异。

常用入口如下：

```text
node src/read.mjs --gil=<样本.gia> --spec
node src/read2spec.mjs --gia=<样本.gia> --outdir=out
node src/emit.mjs --spec=<规格.json>
node src/gts-build.mjs --src=<生成的.ts> --workbench=<工作台目录>
node src/roundtrip.mjs --in=<样本目录> --workbench=<工作台目录>
```

## 发布与安全边界

- 注入目标必须是已存在的节点图，默认写入 `.gil` 副本。
- 不把用户的 `.gil`、`.gia`、游戏日志、遥测数据库和本地临时目录提交到仓库。
- 不把节点图工具的文件层通过结果表述为正式服生效证据。
- 正式发布前必须单独验证玩家实体上的局内存档是否在正式入口带入，以及更新版本对旧存档的兼容性。
- 编辑器的“下次试玩自动填充保存数据”属于试玩链路配置，不能替代正式玩家存档验收。

## 后续维护

升级 `genshin-ts`、节点目录或端口别名后，应先运行离线测试，再用一个已知节点图样本做读回和编译对照。遇到未知节点类型或泛型端口时，优先查阅仓库内的节点图参考实现，保留明确的阻塞报告，不用近似类型生成结果。
